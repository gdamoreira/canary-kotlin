# Operations Guide

> Adapted from canary/docs/operations.md for the Kotlin/JVM engine.
> Canary-Kotlin status: adapted to Gradle distribution + Docker deployment and
> PostgreSQL 16. Upstream C++/MariaDB-specific steps are replaced; where an
> upstream concern survives unchanged, it is kept and the JVM equivalent is
> named explicitly.

## Introduction

This document describes the operational procedures required to run, maintain,
monitor and support a Canary Kotlin server in development, staging or
production environments.

The audience for this document includes:

- System Administrators
- DevOps Engineers
- Infrastructure Engineers
- Server Owners
- Community Managers

This guide focuses on:

- Deployment
- Monitoring
- Backups
- Recovery
- Security
- Upgrades
- Incident Response

```text

    ▼
```

# Deployment Models

## Docker

Recommended for local development, testing and LAN demos.

The repository quickstart is a two-service Compose stack:

- PostgreSQL 16 (`postgres:16-alpine`) with a health check and persistent volume
- Canary Kotlin server built from the repository `Dockerfile`
  (`gradle:9.8.1-jdk25` build stage, `eclipse-temurin:25-jre-alpine` runtime)

Startup:

```bash
docker compose up -d --build
```

Default exposed endpoints and ports:

```text
Canary login/status protocol:  7171
Canary game protocol:          7172
PostgreSQL:                    5432 (mapped unless CANARY_DB_PORT is changed)
```

The upstream C++ quickstart extras (MyAAC website, `opentibiabr/login-server`,
`8080`/`8088`) are not part of this port. The native login server on `7171` is
the entry point.

The quickstart is not a hardened production deployment with default settings.
Before using it outside a trusted local network, change all default passwords,
review published ports, and pin image tags. See
[docker/quickstart-for-beginners.md](docker/quickstart-for-beginners.md).

## Native distribution

Suitable when:

- Maximum control over the JVM is required
- Custom infrastructure exists
- Advanced monitoring is used
- Production hardening is required

Build and run the Gradle distribution:

```bash
./gradlew installDist
./build/install/canary-kotlin/bin/canary-kotlin
```

Typical deployment:

```text
Linux Server
├── Canary Kotlin distribution (build/install/canary-kotlin)
├── Configuration (CANARY_* environment variables)
├── data/ (Lua datapack)
├── PostgreSQL 16
└── Backup storage
```

Run it under a process supervisor (systemd, container entrypoint, or similar)
so crashes are restarted and JVM output is captured.

# JVM Requirements

The server requires a Java 25 LTS runtime. The Gradle distribution generated by
`installDist` includes a launcher script; the JVM can be selected with
`JAVA_HOME` or by placing `java` on the `PATH`.

Recommended JVM flags for production:

```text
-Xms<same order as -Xmx>          # stable heap
-Xmx<heap>                        # see hardware-sizing.md
-XX:MaxDirectMemorySize=<size>    # Netty direct buffers
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=<path>
-Xlog:gc*:file=<path>:time,uptime,level,tags
```

Gradle application start scripts honor `JAVA_OPTS` and the application-specific
`CANARY_KOTLIN_OPTS` variable; operators can also manage options through their
service unit. Size the heap, direct memory and GC as described in
[hardware-sizing.md](hardware-sizing.md).

# Configuration Management

Configuration precedence in the port is:

```text
CLI options > properties file (--config) > CANARY_* environment > defaults
```

Server CLI flags (`ServerCli`):

```text
--config <path>       properties file with config.lua-style keys
--data-dir <path>     datapack directory override
--db-host, --db-port, --db-name, --db-user, --db-password
```

The canonical keys are declared in
`src/main/kotlin/org/opentibia/canary/config/ConfigKeys.kt`. Frequently used
environment variables:

```text
CANARY_DB_HOST, CANARY_DB_PORT, CANARY_DB_NAME, CANARY_DB_USER, CANARY_DB_PASSWORD
CANARY_SERVER_NAME, CANARY_IP
CANARY_LOGIN_PORT (7171), CANARY_GAME_PORT (7172), CANARY_STATUS_PORT (7171)
CANARY_LEGACY_1100_GAME_PORT, CANARY_LEGACY_860_GAME_PORT
```

Best practices:

- Store secrets outside Git
- Version-control non-secret configuration templates
- Document environment-specific overrides
- Review configuration changes before deployment

# Database Operations

## Health Checks

Verify connectivity:

```sql
SELECT 1;
```

Verify player activity:

```sql
SELECT COUNT(*) FROM players;
```

Verify account count:

```sql
SELECT COUNT(*) FROM accounts;
```

## Maintenance

Regular tasks:

- Check indexes
- Remove orphaned records
- Monitor storage growth
- Run `VACUUM`/`ANALYZE` (or `autovacuum`) on the PostgreSQL 16 host

Example:

```sql
VACUUM (ANALYZE) players;
```

PostgreSQL does not need the MySQL `OPTIMIZE TABLE` step used by the upstream
engine; autovacuum plus periodic `VACUUM`/`REINDEX` maintenance covers the same
goal.

## Migrations

Flyway runs automatically on server boot before network traffic is accepted.
Operators should:

- Back up the database before deploying a version with new migrations
- Never edit an applied migration file
- Add schema changes only as `V1__...`–`V21__...` incremental migrations under
  `src/main/resources/db/migration/`

# Database Backup

Example (custom format, compressed by `pg_dump`):

```bash
pg_dump -Fc -h localhost -U canary -d canary -f canary-$(date +%F).dump
```

Plain SQL alternative:

```bash
pg_dump -h localhost -U canary -d canary | gzip > canary-$(date +%F).sql.gz
```

# Recovery Procedures

## Database Restore

```bash
pg_restore -h localhost -U canary -d canary --clean --if-exists canary-2026-10-14.dump
```

For the SQL format:

```bash
gunzip -c canary-2026-10-14.sql.gz | psql -h localhost -U canary -d canary
```

Restore:


# Metrics

The port includes a Prometheus-compatible `MetricsRegistry` with counters,
up/down counters and latency histograms (method, Lua, query, task and lock
latency). The OpenTelemetry SDK exporter from upstream is not ported; scrape the
in-process registry instead.

Monitor trends rather than isolated spikes.

# JVM Diagnostics

For a running server, collect:

```bash
jcmd <pid> Thread.print          # thread dump (dispatcher stalls, deadlocks)
jcmd <pid> GC.heap_info          # heap regions and GC state
jcmd <pid> VM.native_memory      # native/direct memory tracking (if enabled)
jstack <pid>                     # alternate thread dump
```

- Enable `-XX:+HeapDumpOnOutOfMemoryError` before an incident, not after.
- Fatal JVM crashes produce `hs_err_pid<pid>.log`; preserve it with the server
  logs and the exact distribution used.
- Thread dumps identify whether the `GameDispatcher` world thread is blocked in
  database or Lua work; that distinction drives whether the fix is capacity,
  configuration or code.

# Incident Response

## Server Crash

Actions:

```text
Capture logs and hs_err_pid*.log if present
Collect a thread dump if the process is alive but stalled
Preserve the exact distribution/image and configuration
Restart service
```

Do not immediately delete temporary files or logs.

## Database Failure

Actions:

```text
Verify connectivity
Check disk space
Inspect PostgreSQL logs
Restore backup if needed
```

## Data Corruption

Actions:

```text
Stop writes
Create a snapshot
Investigate scope
Restore from backup
```

Never continue operating on a corrupted database.

# Security Operations

## Network Security

Restrict:

```text
5432 (PostgreSQL)
SSH
Administration panels
```

Expose only required services.

## Firewall Example

Allow:

```text
7171  Canary login/status protocol
7172  Canary game protocol
80    Web/API HTTP, preferably redirected to HTTPS
443   Web/API HTTPS
```

Keep PostgreSQL (5432) and SSH restricted to trusted networks unless a
deployment explicitly requires otherwise.

## Access Control

Separate accounts for:

```text
Administration
Development
Automation
Monitoring
```

Avoid shared credentials.

## SSL/TLS

Always use HTTPS for:

```text
APIs and webhooks
Administration panels
Reverse proxies
```

Recommended:

```text
Let's Encrypt
Cloudflare
Reverse Proxy TLS
```

The game protocol itself remains the native Tibia wire protocol; TLS is
terminated by the surrounding web/API infrastructure.

# Operational Runbook

## Startup

Docker:

```bash
docker compose up -d
```

Native distribution:

```bash
./build/install/canary-kotlin/bin/canary-kotlin
```

Verify:

```text
Database connected (Flyway migrations applied)
Map loaded
Players can log in
```

## Shutdown

Graceful shutdown:

```text
Notify players
Save state (the shutdown handler flushes world state atomically)
Stop server
```

Avoid forced termination whenever possible; `SIGTERM` triggers the graceful
shutdown path.

# Disaster Recovery Objectives

Recommended targets:

## RPO (Recovery Point Objective)

```text
≤ 1 Hour
```

Maximum acceptable data loss.

## RTO (Recovery Time Objective)

```text
≤ 30 Minutes
```

Maximum acceptable downtime.

# Conclusion

Successful Canary Kotlin operations depend on:

- Reliable backups
- Continuous monitoring (JVM and PostgreSQL)
- Secure infrastructure
- Controlled deployments
- Documented recovery procedures

Following these practices helps ensure stable gameplay, faster incident
recovery and a safer production environment for both administrators and
players.
